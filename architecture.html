Architecture

A graph-augmented retrieval system over an Obsidian research vault. Local models run on-premise on a dual AMD Radeon AI PRO R9700 workstation; a live Qdrant vector store already serves retrieval, an entity-relation graph (LightRAG) is being built alongside it, and the store is designed to reach Claude Code through a local MCP server. The choice of local models is derived from the NaviMed benchmarks.

What this page is. A description of structure and method — how the pieces connect and why, and what is built versus planned. It reports no performance figures. Retrieval quality, throughput, latency, and energy are out of scope here, and none appear on this page.

System at a glance

Ingest reads the vault and a local model embeds each note into a Qdrant collection, which is live and serves vector retrieval today. The same ingest is being extended to extract entities and relations into a LightRAG graph; that extraction is not yet reliable. A local MCP server that exposes both indexes to the agent is the next step, not a current capability. Substrate

The substrate is the research vault itself: plain-Markdown notes on disk, versioned in git. Nothing is copied into a proprietary store; the notes stay the source of truth, and the indexes are derived, disposable views over them.

Retrieval is hybrid by design, not a single vector database. Two shapes of knowledge are intended to sit side by side:

  • A vector index in Qdrant — built and live. Notes are embedded locally into a vault RAG collection that serves semantic recall today: the fuzzy-prose half of retrieval.
  • An entity-relation graph built with LightRAG — in progress. A local model reads each note and extracts entities and the relations between them, so the store can answer questions that depend on how things connect. Extraction over the vault is not yet reliable, so the graph is not in routine use.

The design goal is a query that draws on both — graph neighbourhood and vector neighbours — with a local model synthesising the retrieved context into an answer. Keeping the two indexes distinct follows the project's retrieval principle: match the primitive to the shape of the knowledge rather than forcing everything through one vector store.

Model selection from NaviMed

The extraction and synthesis roles run on local open-weight models, and which models are viable is decided by the NaviMed hardware envelope, not by guesswork. The benchmark suite already establishes, for this exact workstation, which models load and serve on two R9700 cards, their weight footprint, the KV-cache budget that remains, and how much concurrency each configuration admits.

That envelope maps directly onto role assignment. A small single-card model can run extraction while the second card stays free for other work; a larger model, or the tensor-parallel 70B family, can serve synthesis when the task needs more capability. The published engineering envelope and the released checkpoints are the inputs to that decision. No performance figures are used or shown here — only the load-and-fit envelope that is already public.

Three roles, not a hierarchy

Three parties act on the substrate. They form a triangle rather than a stack: each reads and writes the same vault, and none owns the others.

Role 1

Operator

The researcher curates the notes, asks the questions, and decides what is worth keeping. The vault is authored by a human first; the machinery is downstream of that.

Role 2

Agent

Claude Code queries the store and reasons over grounded context. Today it reaches the vault directly; the planned MCP server will give it a single retrieval interface and a path to propose edits back to the notes.

Role 3

Maintenance

Scheduled local jobs keep the indexes honest: re-ingest changed notes, rebuild the graph and vectors, and flag duplicates, contradictions, and staleness.

On-premise

Every component in the shaded band runs on the local workstation: the vault on disk, the extraction and synthesis models under vLLM on the two R9700 cards, the Qdrant vector store, the in-progress graph, and — once built — the MCP server. Retrieval and embedding happen without an external API call for the local-model roles. Claude Code is the one party at the boundary — a coding agent that consumes the store rather than holding it.

The separation of vaults is enforced in code, not by convention. Only the research vault is ingested. The clinical vault, which holds patient-related material, is excluded at the ingest layer and is never indexed, embedded, or exposed. Nothing patient-related enters this pipeline.

Status — built vs planned

  • Built The NaviMed benchmark suite — the model-selection input.
  • In prog. The LightRAG entity-relation graph over the vault — extraction / ingest not yet reliable.
  • Planned Exposing LightRAG as a local MCP server.
  • Planned Live incremental maintenance and write-back of agent edits.
