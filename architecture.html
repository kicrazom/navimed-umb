Architecture

A graph-augmented retrieval system over an Obsidian research vault. Local models run on-premise on a dual AMD Radeon AI PRO R9700 workstation; a live Qdrant vector store already serves retrieval, and an emergent wikilink graph arm is the decided next step alongside it. The system is developed on two machines by design: a portable dev harness — hybrid lexical + dense retrieval with a frozen evaluation baseline, already serving Claude Code through a local MCP server — runs on a laptop-class GPU, and moves to this workstation by a change of configuration profile, not code. The choice of local models is derived from the NaviMed benchmarks.

What this page is. A description of structure and method — how the pieces connect and why, and what is built versus planned. It reports no performance figures. Retrieval quality, throughput, latency, and energy are out of scope here, and none appear on this page.

Substrate

The substrate is the research vault itself: plain-Markdown notes on disk, versioned in git. Nothing is copied into a proprietary store; the notes stay the source of truth, and the indexes are derived, disposable views over them.

Retrieval is hybrid by design, not a single vector database. Two shapes of knowledge are intended to sit side by side:

  • A vector index — built and live. Notes are embedded locally and serve semantic recall today: the fuzzy-prose half of retrieval. On the workstation this is a Qdrant collection; the portable dev harness keeps the same contract on an embedded local store (with sqlite-vec / DuckDB-VSS as the recorded scaling path — a deliberate decision of 2026-07-04 to prefer embedded backends over a server dependency).
  • A lexical index (BM25) — built, dev harness. Exact names, abbreviations, and Polish inflection are retrieval signals that embeddings blur; a BM25 arm over the same chunks is fused with the dense arm by reciprocal rank fusion, so neither half has to carry the whole query.
  • An entity-relation graph — planned. LightRAG extraction over the vault was evaluated first and set aside as not yet reliable; the decided direction (2026-07-04, custom build) is an emergent graph derived from the vault's own [[wikilink]] topology at index time — the links the researcher already curates, rather than a model's guess at them. The build has not started: the frozen baseline is deliberately graph-free.

The design goal is a query that draws on all of these — graph neighbourhood, vector neighbours, and lexical anchors — with a local model synthesising the retrieved context into an answer. Keeping the indexes distinct follows the project's retrieval principle: match the primitive to the shape of the knowledge rather than forcing everything through one vector store.

The step after the graph is percolation-RAG: edges in the graph carry graduated epistemic status rather than flat truth, retrieval discounts speculation against canon, and a claim promotes only when independent evidence paths converge on it — the retrieval-side application of the project's evidence-percolation model. That layer is design-stage, and it is the reason the graph arm is built from curated wikilinks rather than model-extracted triples alone: the links are the evidence paths.

Measurement layer

Every retrieval change is measured before it is believed. A seed set of Polish questions, each hand-labelled with the note that should answer it, drives a small harness computing recall@k and MRR@k; the hybrid-without-graph configuration is frozen as the baseline, and every subsequent component lands as a measured delta against it, organised as a 2×2 ablation grid — baseline, +reranker, +graph, +both. Each result is stamped with the embedding-model version and chunking strategy, so numbers stay attributable to the configuration that produced them. Consistent with this page's scope, the figures live in the project repository, not here.

Model selection from NaviMed

The extraction and synthesis roles run on local open-weight models, and which models are viable is decided by the NaviMed hardware envelope, not by guesswork. The benchmark suite already establishes, for this exact workstation, which models load and serve on two R9700 cards, their weight footprint, the KV-cache budget that remains, and how much concurrency each configuration admits.

That envelope maps directly onto role assignment. A small single-card model can run extraction while the second card stays free for other work; a larger model, or the tensor-parallel 70B family, can serve synthesis when the task needs more capability. The published engineering envelope and the released checkpoints are the inputs to that decision. No performance figures are used or shown here — only the load-and-fit envelope that is already public.

Three roles, not a hierarchy

Three parties act on the substrate. They form a triangle rather than a stack: each reads and writes the same vault, and none owns the others.

Role 1

Operator

The researcher curates the notes, asks the questions, and decides what is worth keeping. The vault is authored by a human first; the machinery is downstream of that.

Role 2

Agent

Claude Code queries the store and reasons over grounded context. On the dev harness it already retrieves through the local MCP server — a single retrieval interface; planned next are the workstation deployment of that server and a path to propose edits back to the notes.

Role 3

Maintenance

Scheduled local jobs keep the indexes honest. Built on the dev harness: a nightly loop re-embeds only notes whose content changed and re-runs the retrieval evaluation against the frozen baseline, flagging regressions. Planned: duplicate, contradiction, and staleness sweeps.

On-premise

Every component in the shaded band runs on the local workstation: the vault on disk, the extraction and synthesis models under vLLM on the two R9700 cards, the Qdrant vector store, the planned graph, and — once deployed there — the MCP server. Retrieval and embedding happen without an external API call for the local-model roles. Claude Code is the one party at the boundary — a coding agent that consumes the store rather than holding it.

The separation of vaults is enforced in code, not by convention. Only the research vault is ingested. The clinical vault, which holds patient-related material, is excluded at the ingest layer and is never indexed, embedded, or exposed. Nothing patient-related enters this pipeline.

Status — built vs planned

The retrieval substrate exists and is partly in use; the parts drawn dashed in the schematic are planned. Marked to the current build:

  • Built The Obsidian research vault as substrate — Markdown on disk, git-versioned.
  • Built Local models on 2× R9700 under vLLM — extraction and synthesis inference.
  • Built A live Qdrant vector store — a vault RAG collection serving semantic retrieval.
  • Built The NaviMed benchmark suite — the model-selection input.
  • Built A portable dev harness — hybrid BM25 + dense retrieval fused by RRF, with a local MCP server already consumed by Claude Code; moves to the workstation by configuration profile.
  • Built The measurement layer — Polish seed set with ground-truth sources, recall@k / MRR@k harness, frozen no-graph baseline for the ablation grid.
  • Built Nightly incremental maintenance on the dev harness — content-hash re-embedding of changed notes plus a regression check against the frozen baseline.
  • Planned The graph arm — an emergent wikilink graph built at index time (decided 2026-07-04, custom build; build not yet started — the frozen baseline is deliberately graph-free). LightRAG extraction was evaluated first and set aside: not reliable over this vault.
  • Planned Workstation deployment of the MCP server, exposing the graph arm alongside vectors.
  • Planned The graph-RAG query path — graph-neighbourhood expansion joining the fused retrieval, measured as a delta in the ablation grid.
  • Planned Percolation-RAG — the graduated epistemic layer over the graph (next step; see Evidence percolation).
  • Planned Write-back of agent edits into the vault.
  • Planned A PyCharm frontend for the operator.

Status reflects the current state of the build, not a deployed product. The solid and grey-dashed elements of the schematic mirror built and planned; the orange dashed feed marks benchmark-derived model selection.
